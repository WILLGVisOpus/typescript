# Task 2.4 — `decideMfaGate` soft-gate decision (Issue #206 / Phase 2)

**Date:** 2026-04-29
**Branch:** `feat/206-zitadel-soft-mfa-fork`
**Issue:** [#206 — Soft-required MFA umbrella](https://github.com/WILLGVisOpus/VisOpus-Test/issues/206)
**Plan:** Task 2.4

## Goal

After password verification, the fork must decide what comes next:
challenge an enrolled factor, walk the user through enrolment, or just
let them through. Pure decision function so the page-level wiring in
Phase 4 (Task 4.2) can stay thin.

## What landed

### `src/lib/server/visopus-mfa-gate.ts`

```ts
type GateDecision = "satisfied" | "challenge" | "setup";

interface GateInputs {
  session: {
    factors?: { totp?, webAuthN?, otpSms?, otpEmail?, password?, … };
    metadata?: Record<string, Uint8Array>;
  };
  userMetadata: { mfa_skip_grace_until: string | null | undefined };
  hasEnrolledFactors: boolean;
}

function decideMfaGate(input: GateInputs): GateDecision;
```

Decision order (first match wins):

1. **MFA factor verified this session** → `satisfied`. Checks
   `session.factors.{totp, webAuthN, otpSms, otpEmail}.verifiedAt`.
   Password-only sessions don't count — the password factor key is
   intentionally excluded from `MFA_FACTOR_KEYS`.
2. **Recovery-code bypass marker present** → `satisfied`. Reads
   `session.metadata.visopus_mfa_satisfied_via` via Task 2.2's
   `decodeSatisfiedVia`.
3. **30-day skip grace active** → `satisfied`. Parses
   `mfa_skip_grace_until` (ISO string from Zitadel user_metadata,
   mirrored from VisOpus backend by Task 1.5's `/skip` endpoint).
   Malformed/unparseable strings treated as absent.
4. **Has enrolled factors but none verified** → `challenge`. Caller
   provides `hasEnrolledFactors` from a `listAuthenticationMethodTypes`
   call earlier in the request — keeps this function pure.
5. **Else** → `setup`.

### `src/lib/server/visopus-mfa-gate.test.ts`

13 vitest cases covering every decision branch:

- TOTP verified → satisfied
- WebAuthN verified → satisfied
- OTP-SMS verified → satisfied
- OTP-Email verified → satisfied
- Bypass marker present → satisfied
- Grace future → satisfied
- Enrolled, none verified → challenge
- No factors, no grace → setup
- Grace in past → setup
- Password-only does NOT count as MFA → challenge (with hasEnrolledFactors)
- Grace beats hasEnrolledFactors (precedence test)
- Malformed grace string → treated as absent
- `verifiedAt: undefined` does not satisfy

## Plan deviation

- Plan signature took two args `(session, userMetadata)`. Added a third
  required field `hasEnrolledFactors` because the plan's "challenge vs
  setup" branch test (`{ factors: { user: { id: "u" } } }`) doesn't
  actually carry that signal — `factors.user` only tells us about the
  password factor in current Zitadel responses. Keeping the function
  pure means the caller (Phase 4 page wiring) is responsible for
  threading the `listAuthenticationMethodTypes` result in.
- Added `MFA_FACTOR_KEYS` constant rather than spreading the names
  inline — easier to audit and update if Zitadel adds a new factor
  type.
- Defensive: malformed dates and `null`/`undefined` graces all return
  `false` from `isGraceActive` rather than throwing — production data
  could conceivably contain stale junk metadata, no need to crash.
